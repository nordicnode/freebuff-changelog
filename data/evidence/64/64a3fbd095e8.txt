/** Fable 5.1's Bedrock route is BYOK-only. Root and helpers use the public

  data_collection: 'deny' as const,

 * How a suggested followup should be phrased, shared by every agent that ends
 * its turn with suggest_followups.
 *
 * Says nothing about *when* to call the tool — that is each agent's own
 * workflow — only about the shape of the prompt it passes. The style rules and
 * their examples were duplicated per agent and drifted apart immediately: one
 * copy grew an exemplar ("Split this file up") that contradicted the
 * self-containment rule the other copy stated, and fixing one copy left the

 * this is the short restatement agents put in front of the model.
 */

 * confirm first" rule — so there is nothing here for a harness to specialize.
 */
export const SKILL_DISCOVERY_GUIDANCE =

 * When to reach for gravity_index, shared by every agent that offers it.

 * Parameterized rather than copied so the other ~90%, which is the same
 * judgement call in both, cannot drift the way the followup style rules did.
 */
export const gravityIndexGuidance = (deeperResearch = '') =>
  `[freebuff product prompt text omitted]${deeperResearch}[freebuff product prompt text omitted]
- **Look it up early, even unprompted:** The user rarely names the category. When a task means adding a dependency, SDK or API key for something outside the codebase (sending email, sign-in, payments, a hosted database or cache, file storage, an LLM or other AI API, error monitoring, analytics, search, SMS), call gravity_index with \`search\` before you write that integration, using the project's real stack. One search per service the task needs is enough; skip it for services the project already uses.
- **Close the loop:** After you integrate a service you found with gravity_index and the user has configured it (its keys are set and it works), call gravity_index with \`report_integration\`, passing the original \`search_id\` and the service slug as \`integrated_slug\`, once.`

 * behind and the docs drifted two generations out of date.
 */
export const OPUS_MODEL = 'anthropic/claude-opus-5'

/**
 * The model behind Codebuff's paid LITE mode, shared by the orchestrator and

import { DEV_SERVER_STARTUP_GUIDANCE } from '@codebuff/common/constants/dev-server-guidance'

/** Standing Sites guidance shared by Desktop and Cloud harnesses, never per-step injection. */
export function sitesGuidance(
  mode: 'plan' | 'build',
  runtime: 'desktop' | 'cloud' = 'desktop',
): string {
  if (mode === 'plan')
    return `# Sites: Cloudflare, auth, and storage
Use sites_list/sites_inspect to understand existing sites. Plan compatible Worker deployments, D1/R2 storage, and @freebuff/auth integration, but do not provision, deploy, or change secrets in plan mode.`
  return `# Sites: Cloudflare, auth, and storage

Use sites_* tools for agent-managed hosting when the user requests it. Sites covers hosting, D1/R2 storage and Sign in with Freebuff only. It does not replace service research: when you have a gravity_index tool, keep using it to choose any other service (email, payments, an external database, AI APIs, monitoring, analytics), and, when the user has not asked for Sites, for hosting, auth or storage too. Keep the site ID in the workspace, inspect existing resources before creating more, and target preview first. Production publishing needs the user's authorization; preview URLs are also public.

To take an environment offline, use sites_set_published with published=false (or Sites → Unpublish). This retains the deployment, data, secrets and URL; serving stops within 30 seconds. Preview and Production are independent. Updates to unpublished environments stay offline until the user requests published=true. Do not delete data to take a site offline.

${runtime === 'cloud' ? 'When website changes are ready for review, start a dev server in the VM bound to 0.0.0.0 and use cloud_show_dev_server with its port. Follow the Cloud preview networking instructions. A dev-server preview is not a deployment and does not establish Workers compatibility.' : 'When website changes are ready for user review, first show the running dev server using register_preview in the right-side browser panel before offering or attempting a preview deployment. Use a loopback URL and the owned server PID. Install dependencies and start the server only when needed. Reuse a running server, keep hot reload working, and skip this for non-web projects or when the user asks not to preview. A dev-server preview is not a deployment and does not establish Workers compatibility. If preview setup fails, report the blocker rather than silently deploying instead.'}

${runtime === 'desktop' ? DEV_SERVER_STARTUP_GUIDANCE : ''}

Compatibility: deploy prebuilt Cloudflare Worker fetch handlers (ES modules, optionally bundled WASM) plus static assets. Static HTML and Vite/React/Vue/Svelte frontends work with a Worker serving env.ASSETS.fetch(request); Hono and other Workers-compatible fetch frameworks work server-side. Bundle dependencies locally. The backend does not build source or run npm, Node/Bun servers, containers, Python, native addons, persistent filesystems, or background daemons. nodejs_compat is limited compatibility, not a Node server. Next.js SSR and other SSR frameworks require a verified Workers adapter and output matching the deploy manifest; do not upload a normal .next build or assume arbitrary adapter bindings are supported. Prefer a static frontend plus a small Worker for new sites.

Storage: sites_add_storage provisions D1 (SQLite SQL via env.DB) or R2 (objects via env.FILES), isolated by preview/production. These are Workers bindings, not browser SDKs or PostgreSQL connections. Query them on the server; use bound SQL parameters. Initialize/migrate the D1 schema through controlled server-side code and test with local Wrangler D1/R2 first; there is no arbitrary SQL-write tool. Deploy after provisioning to attach bindings. Use D1/R2 for persistent user data; isolate-local Maps and arrays are disposable demo state.

Auth: when login/accounts/per-user data are requested, use sites_enable_auth${runtime === 'desktop' ? If the package or issuer is unavailable, report the setup blocker; never invent credentials. ${runtime === 'cloud' ? 'VM loopback addresses are not reachable by the user’s browser: omit localOrigin for hosted auth and verify browser sign-in on the deployed preview origin. ' : ''}Its fetch SDK works in Workers/Hono (also Bun/Deno); its Next.js adapter does not make Next.js automatically deployable here. A browser-only/static app needs a server Worker for auth. Wrap the handler once per isolate before API/static fallbacks using createFreebuffAuth({ clientId: env.FREEBUFF_CLIENT_ID, issuer: env.FREEBUFF_ISSUER, baseUrl: env.APP_ORIGIN }). These reserved public variables are injected on deploy; use returned development.variables locally, with allowInsecureLocalhost only for loopback development. Never derive baseUrl from a request Host. Preview and production share the OIDC production client with exact callbacks; localhost has a separate development client. No client secret is needed.

Protect every private API with getUser, scope D1 queries/R2 ownership by user.sub (never client-supplied IDs or email), check membership for shared resources, and check isSameOriginRequest for mutations. Personalized responses must be private/no-store. Keep platform credentials and session tokens out of project files, browser storage, logs, and assets. For third-party API keys, direct the user to Sites → Secrets so values stay out of chat. Alternatively use sites_set_secret with a user-provided private file; never read/print its value or put it in chat. Deploy once before setting secrets. The project limit is 25 customer variables across preview and production (the same name in both counts twice); reserved auth variables do not count. Inspect names before adding more, and reuse existing names for rotation.

Before even a preview deployment, build and test locally using wrangler dev/Miniflare (workerd) with the deployment compatibility date, flags, assets, and local bindings. A Node/Bun server or fetch shim alone does not verify Workers compatibility. Check routes/assets, D1/R2 behavior, signed-out 401s, a complete sign-in/callback/session/sign-out flow, two-account data isolation, and foreign-Origin 403s. Report checks blocked by missing accounts or setup; a sign-in redirect alone is not a completed login test. Upload only dedicated public build output via sites_deploy's manifest; keep secrets and source maps out. After the receipt succeeds, open the preview in a browser, check console/network errors and HTML/JS/CSS content types, and repeat the auth checks on its actual origin. HTTP 200 or a successful upload alone does not prove the site renders or auth works. If auth returns 503, inspect safe server diagnostics and reproduce in workerd; do not infer tunnel failure from a generic SDK error or weaken redirect/issuer validation. Distinguish deployed from verified working, and report remaining failures explicitly. Reuse requestId for transport retries; inspect running/unknown operations instead of blindly retrying or switching environments.${runtime === 'cloud' ? '\n\nCloud can show a dev-server preview but has no browser automation tools. Complete available workerd/HTTP checks, then ask the user to perform interactive browser and sign-in checks. Report these checks as pending until the user confirms them; do not claim a complete browser test from HTTP responses alone.' : ''}`
}
